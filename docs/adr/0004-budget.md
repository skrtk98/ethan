# ADR 0004: 予算超過時はそれまでの最良の結果を返す

- 状態: 採用（2026-10-17 改訂）
- 日付: 2026-10-17

## 決定

`Budget` に次の上限を持たせる。キャンセルとタイムアウトは `context.Context` で扱う。

| 項目 | 既定値 | 超過時の挙動 |
|---|---|---|
| `MaxDepth` | 2 | その深さのタスクは分解せず直接実行する |
| `MaxNodes` | 40 | 実行全体で起動できるタスク数（末端のタスクも含む）。超えるサブタスクは起動しない |
| `MaxTokens` | 無制限 | 予約できないモデル呼び出しは `ErrBudgetExhausted` で拒否する |
| `SynthesisReserve` | 0.15 | `MaxTokens` のうちこの割合を、ルートのプランの統合のために取り置く。負の値で取り置かない |
| `MaxConcurrency` | 4 | 同時に実行するモデル呼び出しをセマフォで制限する |

### トークンの予約

モデル呼び出しは、開始前に「入力の見積もり＋出力上限（`MaxTokens`）」を予約する。終わったら予約を解放し、実際の使用量を加える。

- 消費済みと予約中の合計に収まらないとき、他の呼び出しの予約が解放されれば収まるなら、解放を待つ。予約は実際の消費より大きいので、並列の呼び出しが予約を抱えているだけで予算切れにはしない。
- 他の予約が全部解放されても収まらないときだけ、`ErrBudgetExhausted` で拒否して予算切れとする。
- 予約を抱えたまま追加予約を待つ呼び出し同士は、互いの解放を待ち合ってしまう。解放してくれる実行中の呼び出しが他にいないときは、待たずに拒否して予算切れとする。

- 入力の見積もりは既定で、送信するもの全部（システムプロンプト、メッセージ、ツール定義、構造化出力のスキーマ）について「バイト数 ÷ 2」とし、メッセージごとに少しの上乗せをする。英語ではおよそ 2 倍、日本語でも多めになる。`WithTokenEstimator` で差し替えられる。
- アダプタは、呼び出し元から見えないトークンを `Request.Reserve` で追加予約する。1 回の `Generate` の中で行う追加の API 呼び出し（`pause_turn` の再開など）と、プロバイダ側で入力に加わるもの（サーバー側 Web 検索の結果。Claude アダプタは検索 1 回あたり 1 万トークンを見込む）が対象である。
- 失敗した呼び出しも、そこまでに消費した使用量を `Response.Usage` で返し、予算に計上する。
- 消費量が上限に達した時点、または呼び出しやタスクが拒否された時点で `Result.Exhausted` を立てる。

### 統合用の取り置き

トークン予算の一部（既定 15%）を、ルートのプランの統合だけが使える分として取り置く。

- それ以外の呼び出しは、取り置きを除いた分の中で予約する。それを使い切った時点で予算切れとし、新しい作業を止める。プランナーに伝える残りトークンも、取り置きを除いた値である。
- ルートより下のプランの統合は取り置きを使わない。予算切れなら従来どおり見出し付きで連結する。
- ルートで複数のプランを並列に実行し、取り置きに統合が 1 つしか収まらなかったときは、統合できたプランを採用する。

### 予算が尽きたとき

予算切れを、他の失敗とは区別して扱う。

- 予算が尽きたら、新しいサブタスク・別案・継続は起動しない。
- 実行中の兄弟はキャンセルせず、完了を待って結果を回収する（他の種類の失敗では、従来どおり兄弟をキャンセルしてプランを失敗にする）。
- 完了したサブタスクが 1 つでもあれば、未完了の分を `[NOT COMPLETED: ...]` と明記したうえでプランの結果を作り、プランを `StatusPartial` にする。統合も予算切れなら、見出し付きで連結する。
- 部分的な成功は親タスクを経てルートまで伝わる。ルートが部分的な成功なら、`Run` はエラーなしで `Result.Partial` を立てて返す。
- 何も完了しなかったときだけ、`ErrBudgetExhausted` をラップしたエラーを返す。

## 改訂の経緯

当初の実装は、呼び出し前の累計だけで判定し、予約をしていなかった。そのため並列の呼び出しがそろって判定を通過し、アダプタ内部の継続呼び出しも数えていなかった。また、統合の段階でしか連結による救済をしていなかった。実 API での試験では、末端のタスクが 5 つ完了していたのに、兄弟の予算切れでプラン全体が失敗し、何も返せなかった。Codex による批判的レビューでもこの点が指摘され、上の形に改めた。

予約を入れた直後の版では、収まらない予約を即座に予算切れとしていた。実 API での試験では、Web 検索つきの呼び出し（1 回およそ 7 万トークンを予約）が 4 つ並ぶだけで 30 万トークンの予約が埋まり、実際の消費が上限よりずっと少ないうちに 6 つのタスクが同時に拒否され、実行全体が止まった。そこで、他の予約の解放を待つ形に改めた。

その後の試験では予算を本当に使い切り、比較をまとめるはずの分析タスクとルートの統合が実行されず、調査結果を連結しただけのレポートになった。実行全体の価値は最後の統合に集まるので、統合用の取り置きを設けた。

## 結果

- 上限の厳しさは見積もりの精度で決まる。見積もりを超えて消費した呼び出し（想定外のトークン化、見込みより大きな検索結果）があると、合計が `MaxTokens` を超えることがある。その場合も、以降の呼び出しは始まらない。
- 予約は保守的なので、予算の最後の数万トークンは使われずに残ることがある。取り置き分も、予算が尽きなかった実行では使われない。
- 大きな呼び出しが 1 つ拒否されると、それより小さな呼び出しも含めて新しい作業は止まる。予算の残りを細切れに使うより、早く部分結果を返すことを優先する。
