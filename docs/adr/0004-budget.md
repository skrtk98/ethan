# ADR 0004: 予算の配分は管轄外とし、上限を機械的に判定して止める

- 状態: 採用（2026-10-18 改訂）
- 日付: 2026-10-17

## 決定

予算をどう配分するかは、使う側の方針とする。フレームワークは上限を機械的に判定し、超えたら実行全体を即キャンセルしてエラーを返すだけにする。

`Limits` に次の上限を持たせる。キャンセルとタイムアウトは `context.Context` で扱う。

| 項目 | 既定値 | 判定 | 超えたとき |
|---|---|---|---|
| `MaxDepth` | 2 | 分解の前 | その深さのタスクは分解せず直接実行する |
| `MaxTasks` | 40 | タスクの起動前 | 実行全体をキャンセルし、`ErrTaskLimit` を返す |
| `MaxTokens` | 無制限 | モデル呼び出しの前と後 | 実行全体をキャンセルし、`ErrTokenLimit` を返す |
| `MaxConcurrency` | 4 | — | 上限ではなく制御。同時に実行するモデル呼び出しをセマフォで制限する |

- `ErrTaskLimit` と `ErrTokenLimit` は `ErrLimitExceeded` を包む。
- トークンは、累計が `MaxTokens` に達していればモデル呼び出しを始めない。呼び出しの結果で累計が `MaxTokens` を超えたら、その場で実行全体をキャンセルする。超えた呼び出しの使用量は計上するが、応答は使わない（応答が求めたツールも実行しない）。
- キャンセルされた後は、ツールを呼ばない。
- 上限を超えた時点で並列に走っていたものが完了していても、その実行は失敗とする。
- 失敗した呼び出しも、そこまでに消費した使用量を `Response.Usage` で返し、計上する。
- 上限は `Run` の 1 回ごとに数える。途中再開（ADR 0005）した場合は、再開した実行の中で改めて数える。
- 単位時間あたりのトークン数は扱わない。API の流量制限は、SDK の再試行に任せる。
- 上限を超えて失敗しても、`Result` には探索木が残る。完了したタスクの出力を使うか、途中から再開するかは呼び出し側が決める。

## 理由

- 予算内で最善を尽くす仕組み（見積もりによる事前予約、予算切れ時の部分結果、統合用の取り置き）を一度作ったが、複雑さとバグのほとんどがそこから生まれた。見積もりは外れやすく（サーバー側 Web 検索は 1 回の呼び出しで約 10 万トークンを使った）、外れるたびに調整が要った。
- 予算をどう使うのが最善かは、用途によって違う。フレームワークが決めることではない。
- 上限の判定を機械的にすれば、挙動が予測しやすく、テストもしやすい。

## 結果

- `MaxTokens` は保証ではなく検知である。上限を超えた時点で実行中だった呼び出しはキャンセルされ、その使用量はプロバイダから返らないので計上できない。プロバイダの請求は `MaxTokens` を少し超えることがある。確実な上限が必要なら、プロバイダ側の利用額上限などで守る。
- SDK は通信エラーや 5xx の応答を既定で再試行する。サーバーが処理して課金したのに応答が失われた呼び出しは、使用量が返らないので計上されない。流量制限（429）からの回復を優先して、再試行は既定のままにする。止めたい場合は、各アダプタの `WithClientOptions` で再試行の回数を 0 にする。
- 上限を超えると、途中までの成果があっても `Run` は失敗する。成果はジャーナル（ADR 0005）から再開に使える。
- 独自の予算方針を入れたい利用者は、`Model` を包んで呼び出しを制御できる。

## 改訂の経緯

当初は「予算超過時はそれまでの最良の結果を返す」とし、トークンの事前予約、部分結果、統合用の取り置きを実装していた。実 API での試験とレビューのたびに、予約の見積もり不足、予約の取り合い、取り置きの使い方などの不具合が見つかった。予算の配分は管轄外とする方針に改め、これらを取り除いた。
