# ADR 0007: 対象は探索的なタスクに限る

- 状態: 採用
- 日付: 2026-10-19

## 決定

ethan の目的は、探索的なタスクについて、計画からタスクの実行、異常時のキャンセルまでをライブラリの中に閉じ込め、その部分の保守性を保つことである。探索的なタスクとは、どう分解すればよいか事前に分からず、計画を試して比べ、だめなら引き返す必要があるものを指す。

対象とするもの:

- 実行時の分解と、複数の計画の比較・後戻り（ADR 0001、0002）
- 上限による停止と、異常時の実行全体のキャンセル（ADR 0004）
- 探索の記録と途中再開（ADR 0005）
- 探索の末端でエージェントが使うツール
- 探索の最終結果の受け取り（テキスト、または型付きの構造化出力）
- 人の確認（HITL）。ただし「どこで」確認するかを利用者が組み込む方式ではなく、「どういう場合に」確認するかを条件で指定する方式とする。例えば、ツールが入力を見て承認を求める、トークンの消費が上限の一定割合に達したら続行を確認する、など。詳細は別の ADR で決める。

対象としないもの:

- 手順が決まった業務フロー（固定の Chain、Graph、Workflow）
- ツール付きのチャット
- 人の承認を決まった場所に挟む処理

これらは Go の標準的な書き方で実現できる。必要なら、ethan の `Run` を Go のコードから呼ぶ一つの手順として組み込めばよい。固定の計画を返すプランナーや、ワークフローを組み立てる API は提供しない。

## 理由

- Eino などのワークフロー型フレームワークとの比較で、固定フローやチャットの領域は、それらのフレームワークか素の Go のほうが素直に書けることが分かった。ethan が同じ領域に機能を足すと、利用者は 2 つの書き方の間で迷い、コアは複雑になる。
- 探索の中身（どの計画を選び、何を並列に走らせ、いつ打ち切るか）は呼び出し側から見えなくてよい。見えないからこそ、そこを入れ替えても呼び出し側のコードが変わらない。人の確認を「どこで」で指定させると、利用者が探索の中身に依存してしまう。「どういう場合に」なら、探索の構造が変わっても条件はそのまま使える。

## 結果

- 機能を追加するかどうかは、探索的なタスクの計画・実行・キャンセル・記録・再開の保守性に役立つかで判断する。
- `Limits.MaxDepth` で分解をなくす設定は用意しない。分解しないなら、ethan を使わずにモデルを直接呼べばよい。
