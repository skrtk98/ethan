# ADR 0005: イベントログをチェックポイントとし、タスク単位で再開する

- 状態: 採用
- 日付: 2026-10-18

## 決定

実行の途中経過は、イベントを起きた順に追記したログ（ジャーナル）として残す。トレースと途中再開は、どちらもこのログから行う。

- `Journal` インターフェースで書き出し先を差し替えられる。標準実装の `FileJournal` は、1 行 1 イベントの JSON Lines でファイルに追記し、イベントごとにディスクへ同期する。
- ジャーナルは `Run` / `Resume` の呼び出しごとに `JournalTo` で渡す。1 本のジャーナルには 1 つの実行と、それを続けた再開だけを記録する。`Replay` は 2 つ目の `run_started` を拒否する。
- 書き出しに失敗したら、実行全体を止めてエラーにする。抜けのあるログからは正しく再開できないためである。
- イベントには、木を組み直すのに要る情報を載せる。
  - 実行の開始: ゴールとルートのエージェント
  - 分解の決定: プランとサブタスクの中身。ID は木の中の ID
  - 完了: 出力と点数
  - 起動しなかったタスク（刈り込み）: その理由
  - モデル呼び出しごとの使用量（呼び出したタスクの ID 付き）。途中で落ちても、払った分が残る
  - 評価: 点数
  - メモの追加
- `Replay` は、ログからモデルを呼ばずに探索木を組み直し、`Result` を返す。
- `Engine.Resume` は、組み直した木から実行を続ける。
  - 完了したタスクとプラン、分解の決定、点数、メモは再利用し、モデルを呼ばない。
  - 案の選択を記録した直後に止まっていた場合は、選ばれた案の結果でタスクを完了とする。
  - それ以外は、実行中だったものも含めて最初からやり直す。エージェントの対話の途中からは再開しない。
  - 同じログに追記を続ければ、複数回の実行が 1 本のログにつながる。
- 上限（ADR 0004）は実行ごとに数える。使用量の通算は、モデル呼び出しごとの記録を合計したもので、`Result.Usage` と `run_done` / `run_failed` イベントにも残す。
- ログの最終行が書きかけで切れていたら、読むときは無視し、追記を始める前に切り詰める。

## 理由

- イベントはすでに 1 本の経路で順番に発行している。書き出しを足すだけで、並列に書き換えられている木全体を止めずに記録できる。
- 木全体のスナップショットは、整合した瞬間を取るために木全体にロックが要る。
- トレースと再開を同じデータでまかなえる。
- タスクの ID は木の位置から決まるので、同じ分解を再利用すれば、ログと再開後の木が一対一で対応する。

## 結果

- 再開の単位はタスクである。止まった時点で実行中だったタスクの費用は無駄になる。
- 上限を超えた時点で並列に走っていた案が完了していても、その実行は失敗とし、案の選択は確定させない。完了した案は残り、再開時に比較の対象になる。
- 改訂: 当初はエンジンにジャーナルを 1 本持たせていたが、複数回や並行の `Run` が同じログに混ざるため、呼び出しごとに渡す形にした。使用量もタスクの終了時にだけ記録していたが、途中で落ちると失われるため、呼び出しごとに記録する形にした（Codex のレビューによる）。
- 再開時に、エージェントの構成やプロンプトが前回と違っていても検出しない。ログに残った決定と出力をそのまま使う。
- ログはイベントの列なので、外部のツールでも読める。
